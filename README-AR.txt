تحديث موظفي المتاجر وصلاحياتهم — HA محاسبة

هذه حزمة تعديل محلية جاهزة للتثبيت. لم تُطبّق على قاعدة البيانات أو الموقع المنشور تلقائياً.
مهم: رفع ملفات الواجهة وحده لا يفعّل حسابات الموظفين؛ يلزم تشغيل SQL ونشر الدالتين أدناه.

شنو يتغير؟
1. الأدمن الرئيسي يحدد لكل حساب «عدد الموظفين المسموح» من إدارة الحسابات، عند الإنشاء أو تعديل النشاط والعدد. القيمة الافتراضية للحسابات السابقة صفر، وتقدر تغيرها من 0 إلى 100.
2. صاحب المتجر خارج العدد. صاحب المتجر يفتح زر «الموظفون والصلاحيات»، وينشئ معرّفاً وكلمة مرور لكل موظف، ويحدد صلاحياته. الموظف يدخل من شاشة الدخول الاعتيادية نفسها.
3. بيانات الموظف ترتبط بدفتر صاحب المتجر. لا ينشأ مخزون مستقل للموظف، وكل عملية يسجلها النظام باسم منفّذها. صاحب المتجر يشوف السجل من إدارة الموظفين.
4. صلاحيات منفصلة لإنشاء البيع، الآجل والأقساط، الخصم وتخفيض السعر، التعديل، الحذف، الترجيع، المشتريات، إضافة الجهات، عرض المخزون، الكلفة وآخر سعر شراء، الربح، التقارير، الديون، القبض، الدفع، وعرض فواتير بقية العاملين.
5. يوجد اختيار سريع «بيع نقدي فقط». بالوضع الافتراضي يشوف الموظف فواتيره فقط؛ فعّل «عرض فواتير بقية العاملين» إذا تريد يشوف فواتير المتجر حسب بقية صلاحياته.
6. كلفة الشراء لا تُرسل لحساب الموظف إلا بصلاحية الكلفة. صلاحيات إنشاء/تعديل/ترجيع المشتريات تفعّل الكلفة تلقائياً لأن الفاتورة تتضمن أسعار الشراء. الربح صلاحية منفصلة. الكلفة لا تدخل في وصل الزبون.
7. صاحب المتجر يقدر يعدّل الصلاحيات أو يوقف الموظف أو يغيّر كلمة مروره أو يحذف حساب دخوله. الفواتير وسجل العمليات تبقى محفوظة بعد حذف الموظف. الحساب الموقوف محسوب ضمن الحد إلى أن تحذفه. تقليل الحد لا يحذف الموظفين الموجودين؛ يمنع الإضافات الجديدة.

نطاق هذه النسخة
- إدارة الموظفين مفعّلة لنشاط الأسواق/التجزئة، المعالجات، والنشاط الكامل. الموظف بالنشاط الكامل يستخدم فواتير التجارة العامة. الأقسام الهندسية والشخصية والورشة والمولدات تبقى لصاحب الحساب؛ هذا التحديث لا يضيف موظفين لتلك الأقسام.
- واجهة الموظف تدعم الدينار العراقي والوحدة الأساسية للصنف. المواد تُختار من مخزون المتجر؛ إضافة الأصناف وتعديل أرصدتها من صاحب المتجر.
- فواتير الموظف بتاريخ اليوم. التواريخ السابقة، الفواتير المرتبطة بتسديد أو مرتجع، والدفعات المستهلكة تُعالج بقيود آمنة أو بواسطة صاحب المتجر. تعديل الفاتورة بتاريخ اليوم فقط، والحذف يرفض الحركات التي يتوقف عليها مخزون أحدث.
- المعالجات: ترجيع جزئي/كامل من فواتير البيع والشراء، وتسديد الفواتير، وسند قبض/دفع مستقل. تسديد الفاتورة يحدّث دفعاتها مثل واجهة صاحب المتجر، ولا يُكرر الحركة النقدية بسند مستقل إضافي.
- الأسواق: القبض والدفع من تسديد فاتورة محددة حتى يُخصم المبلغ من دينها الصحيح. ترجيع الموظف مفعّل للفواتير التي أنشأها هذا التحديث؛ الفواتير القديمة يعالجها صاحب المتجر. الجزء المدفوع من المرتجع يُرد نقداً، والجزء الآجل يُخصم من الدين أولاً.
- التقارير تجمع الفواتير الواقعة ضمن صلاحيات الموظف. الربح المعروض هو ربح البضاعة قبل المصروفات التشغيلية والضريبة والتوصيل، وليس صافي ربح المنشأة.

الإنترنت والمسودات
- أول دخول وتحميل يحتاجان إنترنت. بعدها تبقى آخر بيانات الموظف وصلاحياته مخزونة بهذا الجهاز عند انقطاع الاتصال.
- عملية الأوفلاين تبقى مسودة، ولا تُعتبر فاتورة نهائية ولا تُخصم من المخزون المشترك حتى يؤكدها الخادم. تظهر تحت «عمليات بانتظار التأكيد».
- عند رجوع الاتصال: حدّث البيانات ثم راجع المسودة وأرسلها. إذا تغيّر المخزون أو الدفتر، لا يستبدل النظام التغيير الجديد؛ يطلب مراجعة العملية.
- إعادة إرسال نفس العملية تستخدم رقماً داخلياً ثابتاً لمنع التكرار إذا انقطع الاتصال بعد نجاح الحفظ. المسودة غير المرسلة أو المرفوضة قابلة للتعديل والحذف. العملية التي تنتظر تأكيداً تُراجع أو يُعاد إرسالها قبل إنشاء نسخة معدّلة.
- تغيير الصلاحيات أو الإيقاف يُفحص عند الاتصال بكل طلب؛ الجهاز المنقطع لا يستلم قرار الإيقاف إلا بعد الاتصال. تسجيل خروج المستخدم بنفسه يحتاج دخولاً جديداً عند العودة.

خطوات التثبيت — بالترتيب
أ. احتفظ بنسخة احتياطية من ملفات موقعك وبياناتك.
ب. من Supabase > SQL Editor شغّل الملف:
   supabase/migrations/202611170001_staff.sql
   يضيف حد الموظفين وجدولي الحسابات وسجل العمليات ودوال الحفظ. لا يستبدل فواتيرك ولا يمسح بياناتها. قابل لإعادة التشغيل.
ج. انشر Edge Functions المرفقة بالاسمين الدقيقين:
   manage-subscribers
   accounting-staff
   المصدر لكل دالة في supabase/functions/اسم-الدالة/.
   دالة accounting-staff تحتاج الملفات الثلاثة معاً: index.ts وdomain.mjs وprocessor-core.mjs.
   من مجلد الحزمة، إذا تستخدم Supabase CLI:
   supabase login
   supabase link --project-ref YOUR_PROJECT_REF
   supabase functions deploy manage-subscribers --no-verify-jwt
   supabase functions deploy accounting-staff --no-verify-jwt
   ملف supabase/config.toml مرفق. الدالتان تتحققان داخل الكود من المستخدم عبر auth.getUser(token). مفاتيح الخدمة تبقى داخل Supabase فقط؛ لا تضع service_role في ملفات الموقع.
د. ارفع ملفات الواجهة الموجودة في جذر الحزمة إلى جذر موقع HA-Accounting، مع استبدال الملفات ذات الأسماء نفسها. مجلد supabase مخصص لتثبيت الخادم؛ لا تحتاج رفعه إلى GitHub Pages.
   احتفظ بملف supabase-config.js الحالي الخاص بمشروعك؛ لم يُضمّن بديل له في الحزمة.
هـ. افتح الموقع وحدّث البرنامج، ثم ادخل بالأدمن الرئيسي وحدد حد الموظفين للحساب المطلوب واحفظ. قيمة صفر تمنع إنشاء موظفين.
و. افتح حساب صاحب المتجر واضغط «الموظفون والصلاحيات»، أنشئ موظفاً، ثم جرّب الدخول به من متصفح/جهاز آخر قبل استخدامه اليومي.

مثال
الأدمن الرئيسي يحدد حد حساب «أسواق أحمد» = 3.
صاحب أسواق أحمد ينشئ موظفين اثنين للبيع النقدي وموظفاً ثالثاً بصلاحية الآجل والقبض.
لا يقدر صاحب الأسواق إنشاء موظف رابع إلا بعد زيادة الحد من الأدمن الرئيسي.
إيقاف الموظف لا يمسح فواتيره، وحذف حسابه يبقي اسم المنفّذ وسجل عملياته.

الفحوص المنجزة
- 80 فحصاً محلياً لعمليات وصلاحيات البيع والشراء والتسديد والترجيع، المخزون، توازن القيود، إخفاء الكلفة، ورفض الوصول لفاتورة موظف آخر بدون صلاحية.
- 17 فحص PostgreSQL/RLS محلياً، تشمل حد الموظفين ومنع تغييره مباشرة، عزل حساب آخر، منع الكتابة المباشرة، رفض تكرار العملية، التعارض، الإيقاف، وبقاء سجل العمليات بعد الحذف.
- فحص واجهة الموظف وتسجيل الدخول والأوفلاين والمسودات وإعادة المحاولة بدون تكرار.
- فحوص رجوع للتعديلات السابقة: استعادة النماذج بعد الخطأ، أزرار المرتجعات، الكشوف التفصيلية، الديون الشخصية، الطباعة وPDF، والتحديث اليدوي.
لم يُجرَ نشر أو اختبار بحسابات الإنتاج على موقعك؛ يلزم تثبيت SQL والدالتين ثم تجربة حساب موظف فعلي حسب الخطوات أعلاه.
